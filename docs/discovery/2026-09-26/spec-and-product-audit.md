# Specification and product audit

Date: 26 September 2026. Baseline: `affb1b73b6d4cf1e4ad5143ad65f4827272b6579`. Scope: the current `physio_clinic_platform` source and every file in `specs/`, assessed as a prototype, not a release diff. No application code, deployed services, or live data were changed or accessed for this audit. Findings below come from source inspection; executable verification by the separate standards audit is reported separately.

Paths starting with `lib/`, `functions/`, or `firestore.rules` refer to `physio_clinic_platform/`. Specification paths are relative to the workspace root. Line references refer to the baseline above.

## Spec axis summary — eight grouped findings

An extensive specification exists, but `specs/scheduling_specs.md:4` calls it **“Draft — pending review.”** It contains architecture choices and implementation code, alongside unresolved policy questions. It is evidence of previous assumptions, not newly approved product requirements.

1. **Critical: access promises are contradicted by the draft itself.** The role matrix denies patients and therapists “View all clinic sessions” (`scheduling_specs.md:2812`); the supplied and implemented rules allow clinic-wide reads. Users can also edit their own role/clinic. Callable authorization checks the supplied clinic, without verifying the target record belongs to it (`firestore.rules:21–57`; `functions/src/index.ts:33–59,299–355`).
2. **High: rescheduling keeps superseded appointments active.** “Marks old session as ‘rescheduled’” (`:2379`) combines with availability treating that status as booked (`availabilityService.ts:65–77`). Repeated full reschedules regenerate old history as extra appointments (`rescheduleService.ts:83–108`). This defect is inherited from the draft.
3. **High: integrity guarantees are incomplete.** “Prevents double-booking” (`:45`) is implemented as separate reads and writes. Retries can inflate completion/no-show counters; cancellation or rescheduling can partly commit before failing. The draft’s “idempotency protection” claim (`:2917`) is not fulfilled by a fresh UI key on each attempt and a non-atomic backend lookup.
4. **High: time semantics conflict.** “Today’s sessions are ‘future’” (`:2918`) conflicts with server rejection of dates `<= today`. The server uses UTC dates; Flutter uses device-local dates; neither applies appointment start time.
5. **Partial: promised admin workflows are unreachable.** “Reschedule All Future” (`:2387`) and multi-selection cancellation (`:2415`) have services but no UI callers. The single-move UI omits the promised slot picker (`:2374`).
6. **Partial: notifications are disconnected.** “Save FCM token … on app startup” (`:2465`) has no call site; range cancellation/full reschedule send no notifications.
7. **Partial: renewal is unfinished.** “Mark hold as ‘used’” (`:2450`) is absent; renewal cannot guarantee slots already booked before hold creation.
8. **Unresolved policy, not a missing approved rule:** the no-show limit outcome is explicitly open (`:2893`). Cancellation/no-show replacement is automatic; credits, fees, notice windows, and clinical discharge are not defined.

Eight grouped findings. The most severe spec issue is the contradiction between promised role/clinic boundaries and effective access.

## Concrete scenarios to use in the redesign discussion

These are proposed examples for agreeing expected behavior, not newly accepted policies or tests that were run.

1. **Move one appointment:** a patient has Monday 10:00, then moves to Wednesday 11:00. Monday becomes available, there is exactly one active appointment, and history retains the move. Current code leaves Monday blocked; current UI cannot choose 11:00.
2. **Move the series twice:** three remaining appointments are moved twice. The patient should still have three remaining appointments unless staff explicitly adds visits. Current selection includes superseded history and can create six new appointments on the second move.
3. **Two receptionists race:** two admins choose the last available therapist slot. Define exactly which command succeeds and how the loser sees updated availability. Current read-then-write does not guarantee one winner.
4. **A 12-visit course with a cancelled third appointment:** decide separately whether attendance target remains 12, a package credit is restored, a fee applies, and a replacement is booked immediately. Current behavior always adds a replacement, increases total to 13, and displays a denominator of 13.
5. **One session left; patient does not attend:** define the earliest legal replacement, allowance effect, notification, and exception handling. Current extension may reuse the original date when no completed/scheduled rows remain.
6. **Cancellation succeeds but replacement cannot be found:** choose whether cancellation stands with an unscheduled entitlement, everything rolls back, or staff explicitly approves an alternative. Current command mutates cancellation first and returns an error later.
7. **Mark attendance twice after a slow response:** the second request should have a defined idempotent or correction outcome. Current backend increments twice because it does not validate the prior session state.
8. **Patient cancels at 08:30 for an 18:00 visit today:** agree a clinic policy in hours and a staff exception rule. Current app offers the action but backend rejects it for the whole UTC date.
9. **Plan ends while next month's slot is already booked by another patient:** decide what renewal priority means without promising capacity that is already committed. Current hold is created without checking those existing bookings.
10. **A receptionist registers a child whose parent already has an account:** define patient identity separately from who logs in and who receives notifications. The current one-profile-per-auth-UID structure has no representation for this relationship.
11. **A therapist works at two locations:** agree membership, global time conflicts, travel time, and clinic-specific visibility. Current user and availability documents each have one clinic, and conflict checks are filtered to the request clinic.
12. **A staff member is suspended:** agree whether access ends immediately and which historical records remain visible to others. Current functions ignore account status, while profile ownership permits changing role/clinic.

## Testability and acceptance gaps

The only committed Flutter test is the generated counter smoke test, and the functions package defines no test command. No emulator rules suite or scheduling test suite was found. The auth provider has injectable service parameters, and date generation is a small pure function; those are useful beginnings. Most backend services capture the global database during module initialization, and screens often query global Firestore directly, making isolated state/authorization tests harder.

Before treating either a rewrite or repairs as reliable, translate the agreed examples into evidence at the boundary where the guarantee must hold:

| Boundary | Meaningful acceptance evidence to add after policy agreement |
|---|---|
| Permission rules and commands | A patient cannot grant themselves role/clinic membership; patient A cannot read patient B's appointment; admin A cannot mutate clinic B by passing a target ID; suspended staff receive the agreed denial. Test both client reads and server commands. |
| Reservation concurrency | Two simultaneous commands for overlapping therapist intervals cannot both commit; a timed-out retry returns the same outcome; patient/resource conflicts follow agreed rules. |
| Appointment lifecycle | Move releases old capacity, repeated move preserves remaining count, attendance retry does not increment twice, and corrections are explicit. |
| Failure boundaries | A forced failure between cancellation and replacement, between plan and session creation, or during notification delivery does not produce an undocumented half-success. |
| Recurrence and time | Clinic midnight, today's appointment before/after its start, finite end/count, conflicting dates, and any supported timezone transitions have agreed results. |
| Entitlement and policy | Purchased/prescribed count, attendance, cancellation, no-show, waiver, credit, and fee reconcile independently under examples agreed with the clinic. |
| Human workflows | Every promised action is reachable; date and time can be changed as specified; history is visible to appropriate people; errors are distinguished from empty lists. |

These are targets for a later implementation plan. This audit deliberately does not silently install a cancellation fee, enforce an invented no-show penalty, choose a clinic jurisdiction, or assume that every competitor feature belongs in the MVP.
